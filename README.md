# Шаблоны нового проекта 1С-Битрикс


Стартовый набор для разработки и настройки проектов на **1С-Битрикс: Управление сайтом**.

Репозиторий используется как базовая заготовка при начале работ над новым Bitrix-проектом: содержит подготовленную структуру пользовательского кода, типовые настройки и заготовки, которые можно использовать повторно.

Цель — не начинать каждый новый проект с пустой установки, а иметь собственную проверенную базу для разработки.

---

## 🎯 Назначение

Starter предназначен для:

* быстрого начала разработки нового Bitrix-сайта;
* подготовки стандартной структуры `/local/`;
* хранения собственных компонентов, модулей и обработчиков;
* подключения общих PHP-, JS- и CSS-инструментов;
* подготовки типовых настроек проекта;
* повторного использования на следующих Bitrix-проектах;
* формирования единого подхода к разработке и сопровождению сайтов.

Репозиторий является **базой разработки**, поверх которой создаётся конкретный проект.

---

## 🏗 Структура проекта

Основной пользовательский код размещается в `/local/`.

```text
/
├── bitrix/                 # Ядро 1С-Битрикс
│
├── local/                  # Пользовательский код проекта
│   ├── components/         # Собственные компоненты
│   ├── modules/            # Собственные модули
│   ├── php_interface/      # Инициализация и обработчики
│   ├── templates/          # Пользовательские шаблоны
│   ├── js/                 # JavaScript
│   ├── css/                # CSS
│   └── ...
│
├── upload/                 # Загружаемые файлы
│
├── index.php
├── .gitignore
└── README.md
```

### Почему `/local/`

Код проекта не следует размещать непосредственно внутри `/bitrix/`.

`/bitrix/` является частью ядра CMS и может изменяться при обновлении системы.

Пользовательские доработки размещаются в `/local/`, что позволяет:

* отделить собственный код от ядра;
* безопаснее выполнять обновления Bitrix;
* контролировать изменения через Git;
* переносить разработанные решения между окружениями.

## ⚙️ Принцип работы

Работа с новым проектом строится примерно так:

```text
Bitrix Starter
      │
      ▼
Создание / установка Bitrix
      │
      ▼
Подключение starter
      │
      ▼
Настройка проекта
      │
      ├── /local/
      ├── компоненты
      ├── модули
      ├── обработчики
      ├── шаблоны
      └── frontend
      │
      ▼
Разработка конкретного сайта
```

Starter содержит только то, что имеет смысл использовать повторно.

Проектная бизнес-логика, настройки конкретного заказчика, реквизиты, данные и уникальная функциональность добавляются уже непосредственно в репозитории конкретного проекта.

Базовый сценарий:

Установить необходимую редакцию 1С-Битрикс и выполнить первоначальную настройку окружения.

### 2. Подключить starter

Получить содержимое репозитория и перенести необходимые файлы в проект.

### 3. Проверить структуру

После подключения пользовательский код должен находиться в `/local/`.

Не следует переносить или изменять файлы ядра без необходимости.

* права доступа;

* агенты;

* интеграции;
* API;
* cron;

* дополнительные модули.

## 🔧 Git

Starter сам является Git-репозиторием.

Базовый рабочий процесс:

```bash
git clone https://github.com/stadigit/bitra.git
cd bitra
```

После начала разработки конкретного проекта создаётся отдельный репозиторий проекта.

Например:

```text
bitra
   │
   └── starter
        │
        ├── project-a
        ├── project-b
        └── project-c
```

При этом **starter не должен превращаться в хранилище конкретных проектов**.

---

## 🔐 Что не следует хранить в Git

В репозиторий не должны попадать:

* пароли;
* API-ключи;
* токены;
* данные доступа к БД;
* ключи внешних сервисов;
* реальные персональные данные;
* содержимое `upload/`, если оно не требуется для разработки;
* кеш;
* временные файлы;
* логи;
* резервные копии;
* файлы, генерируемые системой.

Для секретов следует использовать переменные окружения или конфигурацию конкретного окружения.

---

## 🛠 Рабочее окружение

Starter не привязан к одной конкретной конфигурации сервера.

Проект может разворачиваться:

* локально;
* на Bitrix VM;
* на VPS;
* на тестовом сервере;
* на production-сервере.

Рекомендуется разделять окружения:

```text
local
   ↓
development
   ↓
staging
   ↓
production
```

Изменения сначала проверяются в development/staging и только после этого переносятся в production.

---

## 📦 Разработка компонентов

Собственные компоненты следует размещать в:

```text
/local/components/
```

Например:

```text
/local/components/
└── mycompany/
    └── catalog.products/
        ├── .description.php
        ├── class.php
        ├── template.php
        ├── templates/
        └── lang/
```

Такой подход позволяет отделять собственные компоненты от стандартных компонентов Bitrix.

---

## 🧱 Собственные модули

Для функциональности, которая выходит за рамки одного компонента, рекомендуется использовать собственные модули:

```text
/local/modules/
```

Например:

```text
/local/modules/
└── mycompany.project/
    ├── install/
    ├── lib/
    ├── admin/
    └── include.php
```

Это позволяет постепенно переводить проект от набора отдельных PHP-файлов к структурированному приложению.

---

## 🔄 Обновление starter

Starter развивается отдельно от конкретных проектов.

При добавлении нового универсального решения:

```text
starter
   │
   ├── новое решение
   ├── проверка
   └── commit
```

После этого решение можно использовать при создании следующих проектов.

При переносе изменений в существующий проект необходимо проверять совместимость с:

* версией PHP;
* версией Bitrix;
* установленными модулями;
* структурой конкретного проекта;
* существующей бизнес-логикой.

## 📌 Правила разработки

### Не изменять ядро без необходимости

```text
/bitrix/
```

не является местом для постоянных пользовательских доработок.

### Использовать `/local/`

```text
/local/
```

— основное место для собственного кода.

### Не смешивать starter и бизнес-логику

Starter содержит повторно используемые решения.

Конкретный проект содержит:

* бизнес-правила;
* интеграции;
* данные;
* настройки заказчика;
* уникальные компоненты;
* уникальные процессы.

### Делать изменения небольшими

Один commit должен описывать одну логическую задачу.

Примеры:

```text
Add base event handlers
Add custom component template
Add API helper
Fix user authorization
Add Bitrix cache helper
```

## 👨‍💻 Подход

Основная идея репозитория:

> **Не писать одно и то же дважды.**

Если решение оказалось полезным и может применяться в следующем Bitrix-проекте — оно должно постепенно становиться частью starter.

В результате `bitra` превращается не просто в набор файлов, а в собственную **базу разработки Bitrix**, которая сокращает время старта новых проектов и задаёт единый подход к их структуре и разработке.
